Запуск Cloudflare: 2026-11-03 00:10:45–00:11:29 UTC. Движок и серверный
`validateSubmission` не менялись и не оптимизировались. Это расширение

## Набор

Архив: [replays-heavy](../../../tests/fixtures/replays-heavy/README.md).
Manifest фиксирует SHA-256 бинарных replay и полного состояния эталона.

| Fixture | Seed | Финал | Тиков | Событий | Байтов |
| --- | ---: | --- | ---: | ---: | ---: |
| late-20g | 42 | won, 1 500 линий | 290 484 | 44 629 | 89 267 |
| rotate-20g | 42 | won, 1 500 линий | 290 484 | 49 999 | 100 007 |
| hold-seed7 | 7 | won, 1 500 линий | 16 623 | 50 000 | 100 009 |

`late-20g` добавляет реальные idle ticks и lock resets начиная с уровня 81;
это 80 мин 41,4 с активной игры и тот же маршрут укладки seed 42. `rotate-20g`
добавляет 5 370 попыток поворота на уровнях 81+, включая batches до 32 действий.
`hold-seed7` — независимый победный маршрут seed 7 с 1 876 Hold и 25 312
дополнительными попытками CW/CCW. Его дополнительные повороты израсходовали
event budget на ранних уровнях; high-20G rotation stress покрывает другой fixture.
Попытка поворота не означает успешный поворот или максимальное число wall kicks.

Новые fixtures не содержат переписанного поля/PRNG/таймеров. Дополненные rotation
batches сохраняют **полное** состояние после шага; повторная генерация с этим
усиленным guard дала те же SHA-256, что и измеренные файлы. Отдельная симуляция
декодированных bytes подтверждает состояние. Это синтетические боты, не оценка
человеческой проходимости.

## Проверки

В каждом runtime выполнены ровно 12 проверок:

- три последовательные проверки каждого из трёх fixtures;
- один burst из трёх одновременных `rotate-20g` в трёх разных DO.

**Local workerd: 12/12; Cloudflare: 12/12.** Серверные score, lines, ticks и
isClear совпали с эталоном. Сохранённые тела ответов также содержат level 150.
В очищенном cloud tail — 12 DO-логов, outcome `ok`, без исключений.

Сырые результаты: [local](workerd-local-results.json), [cloud](cloud-results.json),
[очищенный tail](cloud-tail-sanitized.json). HTTP wall time включает сеть,
маршрутизацию и cold start; его нельзя выдавать за CPU. Мало образцов для p95/p99.

Probe импортирует production-функцию `validateSubmission`, но не production
`ValidationDO`/LeaderboardDO. В нём синтетические past claims; HMAC, cookie,
rate limit, SQLite-запись и duplicate guard не входят в **этот** тест. Они
проверялись отдельно в [staging](../../STAGING.md) на коротких реальных сессиях.
Три разных probe DO показывают корректность единичного межобъектного burst,
не сериализацию одной партии и не предел пропускной способности аккаунта.

## CPU остаётся неизвестным

В этом cloud tail снова нет `cpuTimeMs`/`wallTimeMs`. Дополнительный read-only
POST к Cloudflare Workers Observability Telemetry `/keys` с текущим Wrangler
OAuth вернул HTTP 403 `no_access_to_workers_observability`:
[ответ](telemetry-keys.json). Предыдущий GraphQL CPU-запрос вернул 401.
Новые credentials/полномочия не запрашивались, платные настройки не включались.

Таким образом, подтверждены HTTP-успех и точные результаты конкретных тяжёлых
replay, но не численный CPU headroom. Нет доказательства worst case для всех
board/rotation потоков, sustained concurrency или сохранности Free-квот при атаке.
Нельзя оценивать суточную вместимость из HTTP wall time или 15-секундного
application deadline. Аккаунтные Free-квоты staging/probe/production общие.

## Изоляция и удаление

Использован временный `tetris-replay-measure-20261103`, закрытый случайным
`PROBE_TOKEN` (stdin, без сохранения значения). Ни staging, ни production к нему
не привязывались. После тестов migration v2 удалила класс ReplayProbe, затем
Worker удалён. Независимый Cloudflare API подтвердил отсутствие обоих ресурсов
и неизменность версий четырёх рабочих Worker:
[cleanup-verification.json](cleanup-verification.json).

Production по-прежнему остаётся тренировочной версией; тестовые результаты в его
рейтинг не записывались. Облачный запуск не означает разрешение на production.

## Воспроизведение

```sh
npm run fixtures:replay:heavy
npm test
npm run bench:replay:heavy
```

Только при разрешении на создание реальных временных облачных ресурсов:

```sh
npm run bench:replay:heavy:cloud
```

Тяжёлый и обычный cloud runner используют одно имя Worker: **не запускать
параллельно**. Локальные runner тоже используют один порт. `finally` выполняет
уборку, но при аварии процесса нужно независимо проверить ресурсы. Сохраняемые
request/response IDs синтетические; cookie и секреты в отчёт не включены.

Следующее решение перед широким выпуском: получить доступную CPU-телеметрию и
оценить квоты/публичную эксплуатацию либо явно принять оставшийся риск для
ограниченного тестового выпуска. Событийная оптимизация пока не обоснована
измеренным CPU и не добавлялась; если понадобится, нужна полная эквивалентность
эталону, включая checkpoint и scoring metadata.
