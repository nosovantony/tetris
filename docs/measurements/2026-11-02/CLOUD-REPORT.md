# Облачные измерения Cloudflare — 2026-11-02

## Итог

После регистрации workers.dev успешно развёрнут временный Worker
`tetris-measure-20261102` с SQLite-backed Durable Object `Probe`.
Проведены ограниченные последовательные тесты, затем стенд полностью удалён.
Платная подписка, DNS, production-приложения и основной план не менялись.

Основные выводы:

1. Обычный Worker действительно ограничивается CPU: в финальной серии
   тяжёлая нагрузка дала 6/6 HTTP 503, в tail — 6 `exceededCpu`.
2. DO выполнил ту же нагрузку 6/6 раз; tail показал **3 241–3 732 мс CPU**,
   медиана 3 312,5 мс. Следовательно, лимит 10 мс не распространялся на эти
   вызовы DO в данном аккаунте.
3. Явный Cache API работает на проверенном workers.dev-адресе в MXP:
   MISS → 5 HIT. Один `Cache-Control` дал 6 разных ответов.
4. Полноценный replay Marathon 150 не измерен: полноценного движка нет.

## Тариф и ограничения интерпретации

Dashboard пользователя показывает 100 000 запросов в день; прерывания
обычного Worker на 10 мс согласуются с Workers Free. Биллинг/подписки через
текущий OAuth недоступны (403), поэтому статус подписки API независимо
не подтверждён. Платных опций мы не включали.

Нагрузка — не игра, а детерминированный цикл `Math.imul` с зависимостью
следующей итерации от предыдущей и возвращаемой контрольной суммой.
Тест допускает максимум 200 млн итераций на запрос, не пытается исчерпать
30 секунд CPU DO и не подтверждает точный верхний лимит DO.

CPU — **`cpuTime` из cloud Wrangler tail**, в миллисекундах, не HTTP wall time,
не performance.now и не пересчёт локальных цифр.

Tail доставил только часть событий, даже при sampling-rate 0.999. Поэтому
по небольшой неполной выборке НЕ публикуются p95/средние для ядра.
В финальной тяжёлой серии есть все 6 записей DO и все 6 ошибок Worker.
Обёртки обычного Worker над DO иногда отмечены `canceled`, хотя клиент получил
HTTP 200 и DO — `ok`; их не считаем ошибками DO и не суммируем CPU обёртки с CPU DO.

## CPU: одинаковая нагрузка в двух средах

Финальная серия: 200 000 000 итераций, 6 последовательных запросов к каждому
маршруту с паузой 150 мс. Не тест пропускной способности и не доказательство SLA.

| Среда | HTTP | Tail CPU, мс | Tail outcome |
|---|---|---|---|
| Worker, попытка 1 | 503 | 222 | exceededCpu |
| Worker, попытки 2–6 | 503 × 5 | 10 каждый | exceededCpu × 5 |
| DO, попытка 1 | 200 | 3 241 | ok |
| DO, попытка 2 | 200 | 3 270 | ok |
| DO, попытка 3 | 200 | 3 732 | ok |
| DO, попытка 4 | 200 | 3 355 | ok |
| DO, попытка 5 | 200 | 3 677 | ok |
| DO, попытка 6 | 200 | 3 250 | ok |

Ранний прогон показал, что обычный Worker иногда завершает запрос и выше
10 мс, но иногда прерывает его. Это не дополнительный гарантированный бюджет.
Так же тайминги одинакового цикла заметно менялись между сериями — результаты
нельзя использовать для калибровки процессора или пересчёта итераций в мс.

### Упрощённое ядро

В финальной серии по 12 HTTP-запросов к Worker/DO прошли с HTTP 200.
Среди доставленных tail-событий ядра:

- Worker: 7, 10, 5, 4 мс CPU (доставлено 4 из 12).
- DO: 27 и 4 мс CPU (доставлено 2 из 12).

Ядро в облачном маршруте включает **генерацию** синтетического журнала,
encode/decode 30 000 событий, простые bitboard-операции, таймеры, console.log
и формирование ответа. Поэтому это не тот же интервал, что измерялся в Node.
Нет SRS, настоящего 7-bag, Hold, T-spin, HMAC и SvelteKit.

Вывод: обещать replay за 2–5 мс в обычном Worker по этим цифрам нельзя.
Проверка в отдельном DO теперь имеет практическое подтверждение как запасной
путь, но стоимость реального движка ещё предстоит измерить.

## Cache API на workers.dev

Клиент: Node fetch без собственного HTTP-кэша. Запросы последовательные,
одинаковый URL внутри серии; UUID ответа позволяет различать поколения.
Ответ: `Cache-Control: public, max-age=15, s-maxage=30`.
Внешний доступ стенда закрыт временным секретным заголовком; сама кэшируемая
нагрузка — публичный UUID, без пользовательских данных.

| Механизм | Последовательность | Поколений ответа |
|---|---|---:|
| Только Cache-Control | MISS × 6 | 6 |
| caches.default.match/put | MISS, HIT × 5 | 1 |
| Дополнительная проверка TTL | MISS, HIT, позже MISS | 2 |

После ожидания минимум 35 секунд (плюс время CPU-серии) тот же URL дал MISS
и новый UUID. Это подтверждает истечение кэша, но не точный момент границы TTL.
Серии обслуживал colo MXP. Проверки нескольких дата-центров, конкурентного
обновления, stale-while-revalidate и реального лидерборда не было.
`X-Probe-Cache` — заголовок нашего кода, не CF-Cache-Status.

Вывод: для плана подходит **явный Cache API**, а не только заголовок.
Утверждение «2–4 запроса к DO в минуту глобально» по-прежнему неверно:
кэш локален для дата-центра, возможны параллельные промахи. Попадание в Cache
API также не отменяет запуск Worker и не превращает API-запрос в Static Asset.

## Объём и очистка

Выполнено 132 ограниченных HTTP-запроса в трёх сериях. Средняя серия прошла
без tail: Wrangler отказал значению sampling-rate=1; её файлы перезаписаны
финальной серией и она не используется для CPU-выводов.
Нагрузки DO не писали таблицы: маршрут `/sql` в облачном стенде отключён.

После теста:

1. Деплой cleanup-миграции `deleted_classes: ["Probe"]`.
2. Удаление временного Worker через Wrangler.
3. Проверка API: список Workers пуст, список DO namespaces пуст.

workers.dev-адрес аккаунта сохранён. Остаточных тестовых Worker/DO namespaces
нет. Сырые tail-логи с IP/TLS-метаданными не добавлены в репозиторий.

## Артефакты

- `cloud/cloud-results.json`, `cloud/cloud-confirm-results.json`: HTTP-результаты.
- `cloud/*-tail-sanitized.json`: CPU, outcome и контрольные суммы без секретов/IP.
- `cloud/worker.mjs`, `cloud/kernels.mjs`, `cloud/wrangler.jsonc`: код стенда.
- `cloud/cloud-run.mjs`, `cloud/cloud-confirm.mjs`: клиенты ограниченных тестов.
- `cloud/cleanup.mjs`, `cloud/cleanup.jsonc`, `cloud/cleanup-result.json`: очистка.

Клиентские скрипты ожидают локальный файл `.probe-token`; его значения здесь
нет и создавать или деплоить стенд автоматически из основного проекта не нужно.

## Следующие решения для плана

- Убрать гарантии CPU и заменить их замерами полного валидатора, включая
  криптографию, декодирование, реальную симуляцию и враждебные входы.
- При необходимости вынести replay в отдельный ValidationDO, не блокируя
  тяжёлой симуляцией единственный LeaderboardDO.
- Описать Cache API явно, кэшировать только общий топ, не личные ответы.
- Сохранить ограничения Free и учесть DO compute/request quotas: больший
  бюджет CPU на вызов не означает неограниченную бесплатную суммарную нагрузку.
