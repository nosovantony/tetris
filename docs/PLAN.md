# План браузерного онлайн-тетриса (Финальная редакция)

**Статус:** Игра полностью развёрнута в production на https://tetris-web.nosov-antony.workers.dev (режим тренировки 1–150 уровней и рейтинговый режим с HMAC-сессиями, валидацией через `ValidationDO`, `LeaderboardDO` на SQLite, Edge Cache API и персональным рекордом). Staging-окружение https://tetris-web-staging.nosov-antony.workers.dev сохраняется для изолированного тестирования. Все этапы плана (1–7) реализованы, протестированы и верифицированы.  
**Основание:** Результаты эмпирических измерений Node.js/workerd и натурных тестов в Cloudflare (2026-11-02, см. [REPORT.md](measurements/2026-11-02/REPORT.md) и [CLOUD-REPORT.md](measurements/2026-11-02/CLOUD-REPORT.md)), а также верификационный тест параметров [tests/plan-validation.mjs](../tests/plan-validation.mjs).

## 1. Зафиксированные требования и ключевые решения

- **Стек**: Svelte (v5 Runes) + SvelteKit + TypeScript, развёртывание на Cloudflare Workers + Static Assets.
- **Тариф Cloudflare**: строго Workers Free. Платные ресурсы исключены, архитектура спроектирована под бесплатные квоты с подтверждёнными натурными тестами запасами пропускной способности.
- **Формат онлайна**: общий асинхронный онлайн-лидерборд с криптографической защитой сессий и серверной валидацией партий через Replay (без синхронного мультиплеера).
- **Режим игры**: «Marathon 150» — 150 уровней прогрессии со стартом с 1-го уровня для рейтинговой таблицы. Свободный выбор уровня (1–150) доступен в режиме тренировки.
- **Условие победы (Clear)**: 10 линий на уровень $\rightarrow$ 1 500 линий завершают марафон («Marathon Clear») с начислением итогового Time Bonus за меньшее суммарное время. Top-out (поражение) также фиксирует набранный результат в таблице.
- **Управление**:
  - Физическая клавиатура с привязкой к `KeyboardEvent.code` (независимо от раскладки RU/EN).
  - Нарисованный в SVG виртуальный сенсорный джойстик слева (4-осевой секторный гейтинг, мёртвая зона, разделение tap/hold) + крупные кнопки действий справа (вращения, Hard Drop, Hold).
- **Графика и анимации**:
  - 100% векторный интерфейс: чистый SVG + аппаратные CSS-анимации / SMIL, без Canvas и WebGL.
  - Растр запрещён в игровом интерфейсе; допущен исключительно для системных иконок платформы (`apple-touch-icon.png` и `og-image.png`).
- **Зависимости**: минимальные (Svelte, SvelteKit, TypeScript, `@sveltejs/adapter-cloudflare`, Vitest и Playwright в `devDependencies`). Никаких UI-китов, ORM, стейт-менеджеров и сторонних библиотек анимаций.
- **CI/CD**: GitHub Actions в рамках бесплатных минут (линтер, проверка типов, модульные и E2E тесты, сборка, деплой через Wrangler).

## 2. Границы квот Cloudflare Free и подтверждённые эмпирические лимиты

### Суточные квоты бесплатного тарифа (Free Plan):
- **Workers Free**: 100 000 HTTP-запросов/сутки; **10 мс процессорного времени (CPU time)** на входящий запрос к обычному Worker (подтверждено натурным тестом: при нагрузке обычный Worker завершается ошибкой `503 exceededCpu`).
- **SQLite-backed Durable Objects (Free)**:
  - 100 000 запросов к DO в сутки;
  - 13 000 GB-s активности в сутки;
  - 5 000 000 прочитанных строк SQLite в сутки;
  - 100 000 записанных строк SQLite в сутки;
  - 5 GB дискового хранилища;
  - **Лимит CPU time на вызов DO**: натурный тест в аккаунте подтвердил успешное непрерывное выполнение нагрузки **3 241–3 732 мс CPU** (6 из 6 запросов прошли успешно со статусом `ok`).

### Архитектурные принципы защиты от исчерпания квот (по итогам тестов):

1. **Stateless-сессии через HMAC-SHA256**:
   - При старте игры клиент запрашивает сессию через `POST /api/runs`.
   - Web Worker генерирует `runId`, `seed`, `startedAt`, `guestId`, параметры DAS/ARR и возвращает криптографически подписанный токен HMAC-SHA256 в памяти Worker.
   - На старте игры обращений к Durable Objects и записей в базу данных **нет** (0 запросов к DO, 0 записей). Брошенные партии не расходуют квоты хранилища.

2. **Явный Cache API для публичного лидерборда (подтверждено облачным тестом)**:
   - Натурный тест на `workers.dev` показал: заголовка `Cache-Control` недостаточно для автоматического кэширования ответов Worker на edge (все 6 запросов без Cache API дали cache miss).
   - Маршрут `GET /api/leaderboard` использует явный `caches.default.match(request)` / `caches.default.put(request, response)` с TTL `s-maxage=30`.
   - В каждом дата-центре Cloudflare Edge (PoP) ответ кэшируется локально. При наплыве тысяч игроков запрос к origin DO происходит не чаще 2 раз в минуту на каждый активный дата-центр, удерживая суточный объём обращений к DO в пределах 100k запросов.

3. **Изоляция приватного профиля от Edge-кэша**:
   - `GET /api/leaderboard/me` (личный рекорд и статистика текущего игрока) отдаётся с `Cache-Control: private, no-store`.
   - Запрос к SQLite DO выполняется точечно по первичному ключу: `SELECT * FROM leaderboard WHERE guest_id = ?` (ровно **1 прочитанная строка**).
   - Запрещены запросы `COUNT(*) WHERE score > ?` на каждый показ страницы, так как сканирование таблицы из 10 000 записей сожгло бы дневную квоту в 5 млн чтений всего за 1 000 запросов. Точный ранг вычисляется внутри кэшируемого топа (1–100), а для игроков вне топа показывается позиция из периодически обновляемого среза или диапазон.

4. **Двухуровневая архитектура валидации (ValidationDO + LeaderboardDO)**:
   - Поскольку экземпляр Durable Object обрабатывает запросы строго однопоточно, тяжёлая проверка длинного replay внутри `LeaderboardDO` заблокировала бы запросы чтения и записи для других игроков.
   - Поэтому валидация replay разделена:
     - Обычный Worker выполняет быструю проверку базовых лимитов и HMAC-подписи.
     - Для симуляции replay длинных партий (до 1 500 линий) используется изолированный вызов либо легковесного симулятора в Worker (Event-Driven Leap), либо отдельного эфемерного экземпляра `ValidationDO` (`idFromName(runId)`), где лимит CPU составляет секунды, а изоляция предотвращает блокировку лидерборда.
     - Только после успешной верификации подтверждённый счёт атомарно отправляется в постоянный `LeaderboardDO`.

5. **Очистка устаревших сессий (Bounded Pruning)**:
   - Таблица `runs` снабжается индексом `CREATE INDEX IF NOT EXISTS idx_runs_expires_at ON runs(expires_at)`.
   - Очистка выполняется пачками с ограничением: `DELETE FROM runs WHERE expires_at < unixepoch() LIMIT 50`. Наличие индекса гарантирует `rowsRead = rowsWritten <= 50`, исключая O(N) сканирование таблицы.

## 4. Движок игры и детерминированный Replay

### Игровые правила (Guideline-совместимые):
- **Поле**: 10 колонок $\times$ 20 видимых строк (+ 2 скрытые строки генерации 21–22).
- **Генератор фигур**: строго равномерный 7-bag (перемешивание цикла из 7 тетрамино через целочисленный PRNG).
- **Вращения**: SRS (Super Rotation System) с полным набором из 5 проверок смещений (wall kicks) для всех фигур, включая специфичные таблицы для I-тетрамино.
- **Очередь**: отображение следующих 5 фигур.
- **Функция Hold**: фиксация одной фигуры, возможность замены один раз за падение (сброс флага при приземлении).
- **Ghost piece**: векторная полупрозрачная проекция идеального места падения.
- **Drop**: Soft Drop (ускоренное падение) и Hard Drop (мгновенное приземление и фиксация).
- **Lock Delay**: таймер фиксации 30 тиков (0.5 с), до 15 сбросов таймера при успешном перемещении или повороте (Infinity rule).
- **Подсчёт очков**: 
  - Одиночная/Двойная/Тройная линия / Тетрис;
  - T-Spin (Mini, Single, Double, Triple) по правилу 3 углов T;
  - Back-to-Back цепочки сложных очисток;
  - Combo-множитель за последовательные очистки;
  - Time Bonus при финише марафона: $\max(0, 1\,500\,000 - \text{ticks} \times 10)$.

### Формат записи Replay и скорректированные лимиты:
- **Математика длины партии**:
  - 1 500 линий требуют минимум $15\,000 / 4 = 3\,750$ тетрамино (при 100% Тетрисах без дыр).
  - При реалистичной эффективности (75–80%) партия длится $\approx 4\,500–5\,000$ фигур.
  - При 6–8 действиях на фигуру (перемещение, поворот, дроп, фиксация) общее число событий составляет $27\,000–40\,000$.
- **Лимит событий**: установлен в **50 000 событий** (вместо исходных 20 000, которые отсекали бы честную победную игру).
- **Кодирование LEB128**:
  - Событие кодируется парой `[deltaTick, actionId]`.
  - При активной игре 98%+ интервалов между действиями меньше 127 тиков (2.1 с) $\rightarrow$ 1 байт на дельту + 1 байт на действие = 2 байта на событие.
  - 40 000 событий $\approx$ 80–85 КБ в бинарном виде $\rightarrow \approx$ 108–115 КБ в Base64.
- **Лимит тела запроса**: установлен в **160 КБ (Base64)** / **128 КиБ (raw binary)**. Это полностью покрывает часовую победную партию и надёжно отсекает сетевой флуд.
- **Event-Driven Leap симулятор**:
  - На сервере симуляция не делает 216 000 пустых итераций по 1 тику: шаг прыгает к ближайшему из:
    $$\Delta t = \min(\text{тик следующего ввода}, \text{тик шага гравитации}, \text{тик истечения Lock Delay})$$
  - Это сокращает число итераций симулятора в 6–10 раз.

## 5. Прогрессия: 150 уровней и победа

- **Режим**: «Marathon 150» — 10 линий на уровень, всего 1 500 линий.
- **Кривая гравитации (в тиках на 1 клетку падения при 60 FPS)**:
  - **Уровни 1–30**: плавное комфортное нарастание темпа (от 60 тиков [1.0 с/клетка] на 1-м уровне до 6 тиков [0.1 с/клетка] на 30-м уровне).
  - **Уровни 31–80**: высокая скорость (от 5 тиков на 31-м до 1 тика [16.6 мс/клетка] на 80-м уровне), интенсивная работа с очередью и DAS/ARR.
  - **Уровни 81–120**: режим **20G** (гравитация = 0 тиков — мгновенное приземление фигуры на поверхность в момент спавна). Игра базируется на скольжении по блокам (floor sliding) и использовании полных 30 тиков Lock Delay.
  - **Уровни 121–150**: экстремальный режим **20G с компрессией Lock Delay**. Время фиксации плавно сжимается с 30 тиков (0.5 с) на 120-м уровне до 15 тиков (0.25 с) на 150-м уровне.
- **Финал (1 500 линий — Marathon Clear)**:
  - Партия фиксируется флагом `is_clear = 1`.
  - Начисляется Time Bonus за скорость прохождения.
  - Отображается победный экран победы с векторной анимацией.
- **Поражение (Top-out)**:
  - Партия фиксируется с флагом `is_clear = 0` на текущем достигнутом уровне и строках.
- **Режим тренировки**: выбор любого стартового уровня от 1 до 150; результат сохраняется локально в IndexedDB, в публичный лидерборд не отправляется.

## 6. Управление: физическая клавиатура и мобильный SVG-джойстик

### 6.1. Клавиатура (ПК)
- Привязка строго через `event.code` (гарантирует одинаковую работу на русской, английской и любой другой раскладке):
  - `ArrowLeft` / `ArrowRight` — перемещение влево/вправо.
  - `ArrowDown` — Soft Drop.
  - `ArrowUp` / `KeyX` — поворот по часовой стрелке (CW).
  - `KeyZ` — поворот против часовой стрелки (CCW).
  - `Space` — Hard Drop.
  - `KeyC` / `ShiftLeft` — Hold (удержание фигуры).
  - `Escape` — Пауза.
- Таймеры DAS (Delayed Auto Shift, по умолчанию 133 мс) и ARR (Auto Repeat Rate, по умолчанию 16 мс), фиксируемые в крипто-сессии.
- Изоляция событий: `preventDefault()` вызывается строго для назначенных игровых клавиш. Служебные сочетания браузера (`Ctrl+R`, `F11`, `F12`, DevTools) не блокируются. В текстовых полях управление игрой выключается.

### 6.2. Мобильный SVG-джойстик
- **Компоновка экрана**:
  - Высота контейнера: `100dvh` с учётом системных отступов `env(safe-area-inset-bottom)`.
  - Игровой стакан расположен по центру вверху. Джойстик и кнопки — в нижней трети экрана, исключая перекрытие стакана пальцами.
- **Слева: Векторный джойстик на SVG**:
  - **4-позиционный секторный гейтинг (Cross-gating)**: строгие кардинальные сектора (Влево, Вправо, Вниз, Нейтраль). Сектор «Вверх» отключён для предотвращения случайных дропов.
  - **Мёртвая зона (Deadzone)**: внутренний круг $\approx 25\%$ радиуса игнорирует микрокасания.
  - **Гистерезис**: переход между секторами требует явного преодоления порогового угла, устраняя дребезг пальца.
  - **Tap vs Drag**: короткий тап по стрелке стика — дискретный сдвиг на 1 клетку; удержание пальца — включение автоповтора (DAS/ARR).
  - **Векторная подсветка**: сектор и стик подсвечиваются через CSS при отклонении.
- **Справа: Крупные сенсорные кнопки на SVG**:
  - `Rotate CW` (основная большая кнопка под большой палец), `Rotate CCW` (вспомогательная).
  - `Hard Drop` (сверху, отделена пространством для защиты от случайных нажатий).
  - `Hold` (сбоку).
- **Сенсорные события**: Pointer Events с вызовом `setPointerCapture` и обработкой `pointercancel`.
- `touch-action: none` на всей игровой зоне. Полная блокировка системного зума при двойном тапе и контекстного меню по долгому нажатию (`contextmenu: preventDefault()`).

### 6.3. Пауза и сохранение состояния
- При `visibilitychange` или `window.blur` игра автоматически становится на паузу.
- **Сброс зажатых кнопок**: при уходе на паузу флаги ввода принудительно сбрасываются в `false`, исключая улетание фигуры в стенку при возвращении.
- При паузе игровое поле затемняется и скрывается (защита от читерского анализа расстановки).
- Снятие с паузы — через 3-секундный обратный отсчёт.
- Промежуточный буфер событий непрерывно сохраняется в `IndexedDB`. При входящем звонке на телефон прогресс восстанавливается.

## 7. Векторная графика (SVG) и архитектура анимаций

### 7.1. Многослойный SVG-холст
- `viewBox="0 0 100 200"` (10 единиц на ячейку — целочисленные координаты без размытия):
  1. **Слой 1 (статический)**: сетка, фон, боковые рамки стакана.
  2. **Слой 2 (кэшированный)**: зафиксированные блоки поля, перерисовывается только при lock/clear.
  3. **Слой 3 (динамический)**: 
     - Проекция (Ghost Piece) — 4 полупрозрачных блока.
     - Активная фигура — группа `<g transform="translate(x, y)">`, перемещаемая аппаратно без перерисовки DOM.

### 7.2. Аппаратные CSS-анимации
- **Очистка линий**: класс `.line-clear-flash` с GPU-ускорением (`opacity` / `filter`).
- **Hard Drop**: кратковременный световой шлейф падения (CSS fade-out).
- **Lock Flash**: вспышка фиксации через CSS.
- **SMIL**: используется только для декоративных непрерывных эффектов в меню и победном экране.
- **Доступность**: медиа-выражение `@media (prefers-reduced-motion: reduce)` отключает вспышки и резкие эффекты, оставляя мгновенное исчезновение строк.
- **Цветовая независимость**: блоки каждого типа различаются не только цветом, но и уникальным внутренним микроузором/символом SVG (для игроков с дальтонизмом).

## 8. Лидерборд и схема базы данных SQLite (Durable Object)

### Таблицы SQLite в Durable Object:
```sql
CREATE TABLE IF NOT EXISTS runs (
  run_id TEXT PRIMARY KEY,
  guest_id TEXT NOT NULL,
  score INTEGER NOT NULL,
  lines INTEGER NOT NULL,
  level INTEGER NOT NULL,
  created_at INTEGER NOT NULL,
  expires_at INTEGER NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_runs_expires_at ON runs(expires_at);

CREATE TABLE IF NOT EXISTS leaderboard (
  guest_id TEXT PRIMARY KEY,
  player_name TEXT NOT NULL,
  score INTEGER NOT NULL,
  lines INTEGER NOT NULL,
  level INTEGER NOT NULL,
  duration_ticks INTEGER NOT NULL,
  is_clear INTEGER NOT NULL,
  achieved_at INTEGER NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_leaderboard_score ON leaderboard(score DESC);
```

### Безопасность и защита от злоупотреблений:
- Сервер сам вычисляет очки, сгоревшие линии и затраченное время в ходе симуляции Replay. Клиентское значение очков игнорируется.
- Токен сессии проверяется на HMAC-подпись и допустимое время ($\text{time} \ge \text{ticks} \times 16.6\text{ мс}$).
- Идемпотентность: `INSERT INTO runs` по первичному ключу `run_id` предотвращает повторную отправку одного и того же результата.
- Экранирование никнеймов и лимит длины (до 20 символов UTF-8).

## 9. Поэтапный план реализации

### Этап 1. Базовый каркас, SvelteKit и окружение Cloudflare
- Инициализация проекта SvelteKit с `@sveltejs/adapter-cloudflare`.
- Настройка Worker с `LeaderboardDO` (SQLite) и привязкой через Service Binding.
- Настройка локального запуска через `wrangler dev` и верификация деплоя на Cloudflare.
- Базовый пайплайн GitHub Actions: проверка типов, линтинг, сборка.
- **Критерий**: сквозной локальный запуск и чтение/запись в SQLite DO работают одной командой.

### Этап 2. Движок Тетриса, детерминизм и кодек Replay
- Модуль `game/`: поле 10x20, 7-bag, SRS со всеми смещениями, коллизии, комбо, T-Spin, подсчёт очков.
- Формулы 150 уровней: кривая гравитации (1–80 уровней), вход в 20G (81–120), компрессия Lock Delay (121–150).
- Кодек LEB128 для компактного сохранения событий и серверный Event-Driven симулятор replay.
- Модульные тесты Vitest: SRS, матрицы смещений, детерминизм PRNG, синтетические партии на 1 500 линий.
- **Критерий**: 100% повторяемость счёта при воспроизведении replay, симулятор воспроизводит 1 500 линий без ошибок.

### Этап 3. Векторный интерфейс (SVG) и клавиатурное управление ПК
- Компонент игрового стакана на SVG (`viewBox="0 0 100 200"`), рендер активной фигуры через CSS `transform`.
- Панели Next (5 фигур) и Hold на SVG.
- Адаптер ввода с клавиатуры по `KeyboardEvent.code` с таймерами DAS и ARR.
- Логика паузы с затемнением поля, сбросом клавиш и 3-секундным отсчётом.
- **Критерий**: плавные 60 FPS на ПК без лагов и задержек ввода при полном цикле игры.

### Этап 4. Мобильный SVG-джойстик и сенсорное управление
- Векторный SVG-джойстик: 4-осевой гейтинг, мёртвая зона 25%, гистерезис, разделение tap/drag.
- Кнопки поворотов, Hard Drop и Hold под правую руку.
- Обработка Pointer Events с `setPointerCapture`, поддержка `100dvh` и Safe Area.
- Блокировка системных меню, зума и скролла.
- **Критерий**: комфортное прохождение игры на мобильном экране без ложных дропов и соскальзываний пальца.

### Этап 5. Прогрессия Marathon 150 и экраны финиша
- Интеграция полной кривой 150 уровней и режима 20G со скольжением по поверхности.
- Обработка победы на 1 500-й линии (Victory screen, расчёт Time Bonus) и Top-out.
- Режим свободной тренировки с выбором стартового уровня от 1 до 150.
- Сохранение незавершённой партии в `IndexedDB`.
- **Критерий**: подтверждённая проходимость 20G и корректное завершение длинных марафонских сессий.

### Этап 6. Серверная валидация, Cache API и Лидерборд
- Эндпоинты `POST /api/runs` (HMAC токен) и `POST /api/runs/finish` (валидация).
- Двухуровневая валидация (Worker + ValidationDO при необходимости) и атомарная запись рекорда в `LeaderboardDO`.
- Публичный маршрут `GET /api/leaderboard` с явным Cache API (`s-maxage=30`).
- Приватный маршрут `GET /api/leaderboard/me` по прямому первичному ключу (1 строка).
- Страница лидерборда с подсветкой личного результата и защитой от XSS.
- **Критерий**: невозможность фальсификации очков через подделку запроса; Edge-кэш защищает DO от перегрузки.

### Этап 7. Полировка, CSS-анимации и релиз
- Векторные CSS-эффекты: вспышки сгорания линий, след Hard Drop, анимация победы.
- Поддержка `prefers-reduced-motion` и различимые микроузоры блоков для игроков с дальтонизмом.
- Генерация фавиконов и служебных растровых иконок (`apple-touch-icon.png`, `og-image.png`).
- Тестирование на мобильных браузерах (Safari iOS, Chrome Android).
- Настройка GitHub Actions для автоматического деплоя на Cloudflare Workers.
- **Критерий**: готовый к релизу, отполированный онлайн-тетрис с безупречной работой на ПК и смартфонах в рамках бесплатного тарифа Cloudflare Free.
