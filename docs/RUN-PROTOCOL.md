# Рейтинговые партии: протокол v1

Реализация проверена локально и в отдельном [staging](STAGING.md). В production
от 2026-11-02 эти изменения ещё не включены. Перед production нужен отдельный случайный Cloudflare Secret
`RUN_SIGNING_KEY` (не менее 32 байт энтропии), backend migration `v2` и повторные
повторные облачные проверки полного пути после выпуска. Длинные replay прошли отдельный облачный probe,
см. [отчёт](measurements/2026-11-03/REPORT.md); CPU-поля в телеметрии отсутствовали.
Секрет хранится только в backend, не в web bundle/vars/git.

## Выдача партии

`POST /api/runs`, `Content-Type: application/json`, тело `{}`.
Origin обязан совпадать с origin запроса; cross-site запрещён. Ответ — `no-store`:

```text
{ token, claims: {
  v: 1, runId, guestId, rulesVersion, issuedAt, expiresAt,
  config: { seed, mode: "ranked", startLevel: 1, dasTicks: 8, arrTicks: 1 }
} }
```

Все параметры выдаёт сервер. Seed — uint32 из Web Crypto; ID — randomUUID.
HMAC-SHA256 подписывает `run.` + base64url(JSON claims); token состоит из
`base64url(payload).base64url(signature)` без padding. Подпись проверяется через
`crypto.subtle.verify`; принимается только текущая версия правил и этот конфиг.
Тело токена не секретно. Клиент не может менять подписанные параметры.

Гость определяется подписанной HttpOnly cookie `marathon_guest` со SameSite=Strict,
Secure на HTTPS и сроком до года. Для cookie используется отдельный HMAC domain
`guest.`. Run привязан к guestId: одной украденной run-строки без cookie недостаточно.
Очистка cookie лишает доступа к старому рекорду/отправке; аккаунтов и восстановления нет.

Выдача не обращается к DO и не пишет в SQLite. Брошенная партия не создаёт записи.
Отсутствующий/короткий ключ даёт 503, без fallback на известный тестовый секрет.

## Время и паузы

- От выдачи до приёма результата — строго менее 24 часов, включая паузы/восстановление.
- Активная симуляция — до 648 000 тиков (три часа при 60 Hz).
- `durationTicks / 60` не может превышать серверное wall time после issuedAt,
  допуск 1 секунда на погрешность таймеров. issuedAt не может быть > now + 1 с.
- Паузы не входят в активное время. Отдельных серверных pause/resume-запросов нет.
- Скрытие поля и countdown — UX, не криптографическая защита анализа поля.
- После восстановления первый активный тик записывает releases. Fractional tick
  и pending input не сохраняются. Replay остаётся единственным источником результата.

## Отправка и доверие

`POST /api/runs/finish` принимает только `{ token, replay, playerName }`.
`replay` — canonical base64url бинарного кодека TR v1; значения score/lines/level
из дополнительных полей игнорируются. Лимит реального потока JSON — 180 КиБ,
бинарного replay — 128 КиБ, событий — 50 000, действий на тик — 32.
Недостаточно проверять Content-Length: подсчитываются фактически прочитанные байты.
Нужен application/json, Content-Encoding запрещён, ошибки не кэшируются.

Backend проверяет HMAC, guest binding, правила, срок до обращения к ValidationDO.
Каждый run использует отдельный `ValidationDO.getByName(runId)` с SQLite-compatible
namespace, но без записей собственного replay/state в storage. Тяжёлая симуляция
не выполняется в обычном Worker и не находится в обработчике LeaderboardDO.

ValidationDO проверяет сохранённую квитанцию в LeaderboardDO. Если результат уже
принят, повтор возвращает `{ accepted: true, duplicate: true, improved: false }`
без повторной симуляции; первый принятый результат и имя неизменны.
Иначе эталонная tick-by-tick симуляция стартует с подписанного seed/config.
Принимаются `lost`, `won`, `timeout`, но не `playing`, и только точное завершение:
продолжение после терминального тика запрещено. Итог вычисляется сервером полностью.

После проверки — одна SQLite-транзакция принятия run и обновления лучшего счёта.
Квитанции хранятся до deadline и удаляются ограниченными пачками; старые токены
всё равно отклоняются до вызова DO. После потери ответа можно повторить запрос.
Принятые одинаковые/меньшие очки не заменяют личный рекорд.

## Сохранения и интерфейс

Тренировка остаётся режимом по умолчанию; рейтинг выбирается явно, всегда с уровня 1.
При ошибке выдачи нет незаметного переключения на локальную партию с обещанием рейтинга.
В IndexedDB к состоянию добавляется ticket. Структурная клиентская проверка ticket
не проверяет HMAC и не заменяет серверную проверку. Изменённый snapshot не даёт
изменить серверный счёт: отправляется лишь replay, а не snapshot/score.
Готовая рейтинговая партия остаётся в слоте до принятия результата, поэтому reload
позволяет повторить отправку. Новая партия заменяет этот единственный слот.
После превышения лимита событий игра продолжается локально, отправка отключена.

## Кэш, профиль и защита квот

`GET /api/leaderboard` использует явные Cache API match/put с каноническим ключом
по origin/rulesVersion, без cookies и произвольных query. TTL — 30 секунд,
`X-Leaderboard-Cache: HIT/MISS/BYPASS`. Не кэшируются ошибки и персональные данные.
Одновременные MISS могут обращаться к DO: это не строгая гарантия «два запроса в минуту».
Кэш локален PoP. `/api/leaderboard/me` всегда `private, no-store`, guest берётся
из подписи cookie; запрос к SQLite по составному первичному ключу, без ранжирующих COUNT.

Web rate-limit binding `RUN_RATE`: приблизительно 30 start и 30 finish в минуту
на IP/PoP (ключи разделены по маршруту), namespace `15026061102`.
Общий NAT может ограничить несколько игроков. Лимит приблизительный и не глобальный,
не является гарантией сохранности суточных квот. ValidationDO допускает одну проверку
на run одновременно и даёт двухсекундный in-memory cooldown после ошибки.
Это не сохраняется после eviction и не заменяет антибот-защиту.

## Ограничения и необходимые измерения

HMAC защищает параметры и привязку результата; replay защищает от произвольных очков.
Протокол **не доказывает человеческую игру**, не препятствует ботам, поиску seed,
офлайн-планированию, копированию событий и анализу на паузе. Origin — защита браузерных
запросов, не аутентификация API от скриптов. Cookie — bearer credential.
Ключ пока один: его замена инвалидирует cookie и незавершённые токены.

Симуляция ограничена 15 секундами wall time с проверками/yield каждые 4096 тиков;
при превышении — 503 без записи результата. Это прикладной защитный бюджет, не
измерение Cloudflare CPU и не доказательство пригодности любого полного марафона.
Проверены короткие терминальные партии, seeded потоки, полный action-only марафон
на 1 500 линий, трёхчасовой timeout и вариант с 50 000 событий, в том числе
в отдельном облачном probe. Это не worst-case proof: CPU-поля tail не вернул.
Сквозная staging-проверка коротких партий прошла без отключения HMAC/времени.
Перед широким выпуском нужны дополнительные seed/
тяжёлые действия, CPU-телеметрия и проверка Free-квот; при необходимости — событийная оптимизация с точной
эквивалентностью эталону. Не обещать антибот-рейтинг или неограниченный трафик.

## Локальная настройка

Скопируйте `workers/backend/.dev.vars.example` в соседний `.dev.vars` и задайте
локальный ключ длиной минимум 32 символа. Не используйте этот ключ в production.
E2E использует отдельный заведомо тестовый ключ и временную SQLite; облака не касается.
Production Secret должен задаваться отдельно через защищённый ввод Wrangler.
